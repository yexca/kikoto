# Translate with AI

The `ai_translation` workflow, its items, review and acceptance.

A Translate with AI submission is one `ai_translation` workflow run with one job for one work. Its `translation_item` rows are the units that run and are reviewed: one work, one target metadata language (`ja-jp`, `zh-cn`, `zh-tw`, `en-us` or `ko-kr`), one category (`title`, `description`, `tag`, `file_name`, `folder_name` or `lyrics`) and one subject (a tag id, a media item id, a folder path below the work folder, or the audio item of a track). `engine` is `llm`. `dedup_key` names the object: language, category and subject, plus the work for everything except a shared tag name, which is one object across the library. A partial unique index on the key over the active states `queued`, `requesting`, `ready` and `uncertain` keeps an object that is running or waiting for review from being requested twice; any other state leaves it missing again. The run input names the languages, categories, provider and model; an item keeps the provider, model, configuration digest and policy digest it was planned with, a `detail_json` of what its category needs (the display name's path, the lyrics source location, work folder and file extension, the original language, the number of lyrics chunks), its source text and digest, its result, the lyrics chunks already translated with the next chunk index, and who requested and reviewed it.

A submission plans only what has no value in a language: a title or description without an edition, manual value (the language's own or the fallback one every language shows) or accepted translation; a shared tag without a name the language shows; a local file or folder without a display name in that language, other than in the original language, outside `lyrics_kikoto`, of at most 512 bytes, and with words besides numbering such as `Track01` or `mp3`; and the lyrics of a local track the request lists without an assignment in that language. Every lyrics entry names a lyrics file of the work family to translate from; a request with an entry without one is refused as `invalid_translation_request`, and a run never transcribes. Work metadata is assessed against the LLM provider's receive maximum before anything is queued.

The job sends each language's queued items: titles, descriptions and tag names in one request, display names in batches of at most 64 names and 8 KiB as tag-shaped entries, and lyrics in chunks of 128 lines. Before every request it rechecks the requester's permission for the category, the provider digest, the policy digest and the source, and assesses the complete source with the policy; a refused item is `invalid` (`permission_changed`, `provider_changed`, `policy_changed`, `source_changed`) or `policy_blocked`. An item is `requesting` while its request is out, together with the run's cancellation check. A request that never left fails it (`endpoint_unavailable`, or `request_too_large` for a body above 128 KiB), as do a definitive rejection (`upstream_rejected` or a Kikoto Helper failure) and an answer that cannot be used (`invalid_output`, `invalid_lyrics_output` or `translation_output_too_large`). A request whose headers left and whose answer was lost, any other error status, and a restart or cancellation while the request is out leave it `uncertain` (`upstream_result_unknown` or `cancelled_result_unknown`), and an answer that arrives after the cancellation keeps that state. A stop that interrupts a request before it leaves queues the item again. Between requests the job yields to other queued work as a transcription does. A run cannot finish while items are queued or requesting; one whose items are completed or stopped resumes without repeating finished requests or lyrics chunks. It succeeds when every item reached review, is `partial` when some stopped, and fails when none did.

A retry from a run queues the run's failed items while preserving results that only need to be applied again. Lyrics whose translated chunks could not be used (`invalid_lyrics_output`, `translation_output_too_large`) are translated again from the first chunk. A source, provider or policy change requires a new request, and an object that got a value meanwhile (`name_exists`, `lyrics_exist`) is not missing any more. An item with an unknown result is queued again only by `POST /api/translation/items/resend` with `acknowledgeUncertain`, and a run retry leaves it untouched.

A finished item is `ready` and is applied by accepting it. The `translation_settings` app setting holds `autoAccept`, on when the row is absent and readable and writable by `sources:write` through `/api/translation/settings`; the interface does not offer it. With auto-accept on, the job accepts every item the moment it is `ready`, through the same acceptance as a reviewer and as its requester, as soon as its result is complete. A refusal fails the item with the refusal as its `failure_code` (`permission_changed`, `source_changed`, `provider_changed`, `policy_changed`, `policy_blocked`, `name_exists`, `lyrics_exist`, `lyrics_folder_blocked` or `accept_failed`) and leaves its result in place; the run's other items continue. Resending an item whose result acceptance could not write (`permission_changed`, `lyrics_folder_blocked`, `accept_failed`) returns it to `ready` and accepts it again as the resending account without another request; an item whose source, provider or policy changed needs a new request. With auto-accept off, finished items wait for review. Every account with the category's permission reviews any item: `metadata:sync` and `library:write` for titles, descriptions and tag names, `library:write` for display names and lyrics. Acceptance rechecks the reviewer's permission, the provider and policy digests, the policy class of the source and the source itself, and marks a changed item `invalid` instead of applying it; there is no expiry otherwise. It settles the item from `ready` to `accepted` in the transaction that applies it, so concurrent acceptances apply once. A title or description becomes the `work_llm_translation` value with its review history, a tag name the `metadata_tag_llm_name` of that language, and a display name an `llm` row of the display name tables. Lyrics are published as [speech transcription](speech-transcription.md#speech-transcription) publishes them, with origin `translation`, once the lyrics file they were read from is unchanged; the item settles in the transaction that assigns the published file and records its path as `appliedPath`. A display name someone gave the file or folder by then, or lyrics assigned to the track in the language by then, is kept, and the item becomes `invalid` with `name_exists` or `lyrics_exist` instead. The Translation page reads runs by status and items by state across works, `accepted` items as what translations wrote; neither keeps a copy of the other's state. In Demo, which translates nothing, both lists are empty.

The `lyrics_ai_attribution` setting, on by default, decides whether a lyrics file written by speech recognition or translation starts with a line in the lyrics' language naming the speech model or the translation model, in the five interface languages and English for the fallback. LRC takes a `[00:00.00]` line, WebVTT and SRT a cue from 0 until the first cue (both shown together when the first cue starts at 0, SRT identifiers renumbered), ASS a Dialogue line copied from the first one, and plain text a first line. Lyrics parsing for translation removes a recognized line before sending, and the result receives its own. The line is added when the result is made, so turning the setting off affects files written afterwards.
