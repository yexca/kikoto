# 시작하기

## 요구 사항

- Docker 및 Docker Compose.
- 로컬 개발용(선택 사항):
  - Go 1.26.9.
  - Node.js 24.19.0 및 npm 11.17.0.

## Docker로 실행

빈 디렉터리에 `docker-compose.yml`을 내려받은 뒤, Docker Hub에 게시된 최신 이미지를 받아 시작합니다. 시작하기 전에 비밀번호는 필요하지 않습니다.

```sh
docker compose up -d
```

기본 이미지는 `yexca/kikoto:latest`이며, 릴리스 워크플로가 공개 릴리스마다 이를 갱신합니다. `docker compose up -d`는 없는 이미지를 받아오고 `latest`는 항상 새로 받아옵니다. `docker compose restart`는 현재 컨테이너 이미지를 그대로 다시 사용합니다. 고정한 버전을 업그레이드할 때는 `docker compose up -d`를 실행하기 전에 `KIKOTO_IMAGE`를 원하는 태그나 다이제스트로 바꾸세요. 재현 가능한 배포를 원하면 `.env`의 `KIKOTO_IMAGE`에 검토를 마친 버전이나 다이제스트를 지정하세요.

```sh
KIKOTO_IMAGE=yexca/kikoto@sha256:d51500d0155694908e392e6f936c24610eac23e16072bcef7b03c229d89953ca docker compose up -d
```

다음 주소를 엽니다.

- 프런트엔드: `http://127.0.0.1:7655`

처음 시작하면 프런트엔드에 **Kikoto 설정**이 표시됩니다. `docker compose logs kikoto` 또는 `config/setup-token`에서 확인한 일회용 설정 토큰을 입력한 다음, 관리자 사용자 이름과 비밀번호를 정하세요. 잊어버린 비밀번호를 재설정하려면 [관리자 설정 및 복구](../../operations/security.md#administrator-setup-and-recovery)를 참고하세요.

프로덕션 Compose 스택은 웹 애플리케이션과 API를 함께 `7655` 포트로 게시합니다. `7659` 포트는 컨테이너 내부의 백엔드 포트이며, 개발용 Compose 스택에서만 별도로 게시됩니다.

기본 런타임 마운트는 다음과 같습니다.

- `./config:/config`
- `./cache:/cache`
- `./data:/data`

공개 읽기 전용 인스턴스에는 `deploy/compose/demo.yml`을 사용하세요. 게시된 이미지를 받아 사용하며 `./demo` 아래의 별도 마운트를 사용합니다. 후보 작품 폴더는 `./demo/data` 아래에 두세요. 전용 시작 워크플로는 전 연령 대상이며 영구적으로 무료인 작품만 검증하여 색인합니다. [Docker](../../operations/docker.md#demo-stack)를 참고하세요.

## Android 클라이언트

서명된 Android APK는 프로젝트 GitHub Releases에 첨부됩니다. 클라이언트는 자신의 버전을 연결된 서버와 비교합니다. 클라이언트가 서버보다 오래된 경우 일치하는 릴리스를 안내하고, 클라이언트가 더 새로운 경우 서버를 업데이트해야 할 구성 요소로 알려 줍니다. 네트워크 오류가 발생하면 별도의 다시 연결 동작이 유지됩니다.

Kikoto는 Android 패키지를 조용히 설치하지 않습니다. 릴리스를 열고 APK를 설치하는 과정은 사용자가 확인하는 Android 시스템 절차로 그대로 유지됩니다.

## iOS 클라이언트

각 GitHub Release에는 서명되지 않은 iOS IPA인 `kikoto-<version>-unsigned.ipa`도 포함됩니다. iOS는 내려받은 상태로는 이 파일을 설치할 수 없으며, 사이드로딩 도구가 설치 중에 사용자의 Apple 계정으로 다시 서명합니다. Android 클라이언트와 마찬가지로 자신의 버전을 연결된 서버와 비교합니다.

## 라이브러리 처음 설정

1. 지원되는 오디오 작품 폴더를 `data/` 아래에 두거나, 저장 디스크마다 `data/`의 폴더로 마운트하세요(아래 참고).
2. Docker 스택을 시작하고 프런트엔드를 엽니다.
3. 관리자 계정이 만들어지면 **라이브러리 설정**이 열립니다.
   - **표준**(`data/` 디렉터리 전체를 하나의 라이브러리로 사용) 또는 **스토리지 풀**(`data/`의 선택한 첫 번째 단계 폴더 각각이 별도의 디스크 또는 클라우드 드라이브) 중에서 선택하세요. 풀 모드에서는 새로 가져오는 파일(Fetch)을 받을 **Fetch 풀**도 선택합니다. 나중에 모드나 Fetch 풀을 바꾸면 확인을 요청하며, 사이트가 점검 상태인 동안 영향을 받는 파일을 옮깁니다.
   - 라이브러리를 스캔하세요. 스캔은 제공처 메타데이터를 기다리지 않고 로컬 작품을 찾아냅니다.
   - 업그레이드로 이전의 사용자 지정 워크플로가 유지된 경우 검토하세요. Kikoto는 프리셋과 정확히 일치하는 항목을 비활성 트리거로 변환할 수 있으며, 일치하지 않는 정의는 내보낼 수 있습니다. 새로 설치했거나 사용자 지정 워크플로가 없는 상태에서 업그레이드했다면 이 단계는 건너뜁니다.
   - 원한다면 메타데이터 동기화를 시작하세요. 백그라운드에서 실행됩니다.
   - 시작할 때와 폴더가 바뀔 때 스캔을 실행할지 정하세요. 새로 설치한 경우 둘 다 꺼진 상태로 시작하며, 나중에 워크플로에서 켤 수 있습니다.

**나중에**를 누르면 다음에 방문할 때까지 설정이 닫힙니다. 이전 릴리스에서 업그레이드한 인스턴스는 표준 레이아웃과 스캔 트리거를 그대로 유지하지만, 스토리지 풀로 전환할지 선택하기 위해 이 설정이 표시됩니다. 풀로 전환하면 나머지 설정 단계에 앞서 새 로컬 스캔을 실행합니다. 전환하는 동안 관리자에게는 진행 상황이 표시되고, 다른 사용자에게는 점검 안내가 표시됩니다. 전환에 실패하면 디스크를 확인한 뒤 다시 시도할 수 있습니다.

### 스토리지 풀

디스크나 클라우드 드라이브를 각각 데이터 디렉터리의 별도 폴더로 마운트하세요. 예를 들면 다음과 같습니다.

```yaml
volumes:
  - ./config:/config
  - ./cache:/cache
  - ./data:/data
  - /mnt/disk1:/data/disk1
  - /mnt/cloud:/data/cloud
```

Kikoto는 선택한 각 폴더에 `.kikoto-pool` 마커를 기록합니다. 디스크가 마운트되지 않으면 해당 폴더는 비어 있고 마커도 없으므로, 풀은 오프라인으로 표시되고 스캔은 그 풀의 작품을 누락으로 보고하지 않고 그대로 둡니다. Fetch는 파일을 받는 풀 안에서 스테이징하고 게시하므로, 모든 게시는 한 디스크 안에서의 이름 변경으로 이루어집니다. 가져오기 전에 설정 -> 라이브러리에서 Fetch 풀을 선택하세요. 선택하기 전까지는 Fetch가 무엇을 구성해야 하는지 안내합니다.

## 빌드 검증

아래 명령은 소스 체크아웃을 검증합니다. 완전하고 일관된 저장소 검사에는 해당하는 [Makefile](../../../Makefile) 타깃을 사용하는 것이 좋습니다.

백엔드(소스 체크아웃에서만):

```sh
cd backend
go test ./...
```

프런트엔드(소스 체크아웃에서만):

```sh
cd frontend
npm ci --strict-allow-scripts
npm run build
```
