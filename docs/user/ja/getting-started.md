# はじめに
[English](../en/getting-started.md) · [简体中文](../zh-Hans/getting-started.md) · [繁體中文](../zh-Hant/getting-started.md) · [日本語](../ja/getting-started.md) · [한국어](../ko/getting-started.md)

## 動作要件

- Docker と Docker Compose。
- ローカルで開発する場合は任意:
  - Go 1.26.9。
  - Node.js 24.19.0 と npm 11.17.0。

## Docker で実行する

空のディレクトリに `docker-compose.yml` をダウンロードし、公開されている最新の Docker Hub
イメージを取得して起動します。起動前にパスワードは必要ありません。

```sh
docker compose up -d
```

既定のイメージは `yexca/kikoto:latest` で、リリースワークフローが公開リリースごとに更新します。
`docker compose up -d` は、存在しないイメージを取得し、`latest` は常に取得します。
`docker compose restart` は現在のコンテナーイメージをそのまま再利用します。
固定バージョンをアップグレードするときは、`docker compose up -d` を実行する前に
`KIKOTO_IMAGE` を目的のタグまたはダイジェストに更新してください。再現可能なデプロイを行うには、
`.env` の `KIKOTO_IMAGE` に、確認済みのバージョンまたはダイジェストを設定します。

```sh
KIKOTO_IMAGE=yexca/kikoto@sha256:d51500d0155694908e392e6f936c24610eac23e16072bcef7b03c229d89953ca docker compose up -d
```

次のアドレスを開きます。

- フロントエンド: `http://127.0.0.1:7655`

初回起動時、フロントエンドに **Kikoto のセットアップ** が表示されます。
`docker compose logs kikoto` または `config/setup-token` にある 1 回限りのセットアップトークンを入力し、
その後、管理者のユーザー名とパスワードを選択します。忘れたパスワードをリセットするには、
[管理者のセットアップとリカバリー](../../operations/security.md#administrator-setup-and-recovery)を参照してください。

本番用の Compose スタックは、Web アプリケーションと API を同じポート `7655` で公開します。
ポート `7659` はコンテナー内部のバックエンド用ポートで、開発用の Compose スタックでのみ
個別に公開されます。

既定のランタイムのマウントは次のとおりです。

- `./config:/config`
- `./cache:/cache`
- `./data:/data`

公開用の読み取り専用インスタンスには `deploy/compose/demo.yml` を使用します。公開済みの
イメージを取得し、`./demo` 配下の個別のマウントを使用します。候補となる作品フォルダーは
`./demo/data` に置いてください。専用の起動ワークフローは、全年齢向けで恒久的に無料の作品のみを
検証してインデックスします。[Docker](../../operations/docker.md#demo-stack) を参照してください。

## Android クライアント

署名済みの Android APK は、プロジェクトの GitHub Releases に添付されています。
クライアントは自身のバージョンを、接続先サーバーのバージョンと比較します。古いクライアントには
対応するリリースが案内され、新しいクライアントには更新すべきコンポーネントがサーバーであると
表示されます。ネットワーク障害の場合は、別途 再接続 の操作が残ります。

Kikoto は Android パッケージをサイレントにインストールしません。リリースを開いて APK を
インストールする操作は、これまでどおりユーザーが確認する Android システムの手順です。

## iOS クライアント

各 GitHub Release には、署名されていない iOS 用 IPA `kikoto-<version>-unsigned.ipa` も含まれます。
iOS ではダウンロードしたままではインストールできません。サイドロード用ツールが、インストール時に
お客様ご自身の Apple アカウントで再署名します。Android クライアントと同様に、自身のバージョンを
接続先サーバーのバージョンと比較します。

## 最初のライブラリ設定

1. 対応する音声の作品フォルダーを `data/` の下に置くか、各ストレージディスクを
   `data/` のフォルダーとしてマウントします（下記を参照）。
2. Docker スタックを起動し、フロントエンドを開きます。
3. 管理者アカウントが作成されると、**ライブラリを設定** が開きます。
   - **標準**（`data/` ディレクトリ全体を 1 つのライブラリとして扱う）または
     **ストレージプール**（`data/` 直下の選択した各フォルダーを、それぞれ独立したディスクや
     クラウドドライブとして扱う）を選択します。プールモードでは、新しい取得（Fetch）を
     受け取る **Fetch プール** も選択します。後でモードまたは Fetch プールを変更する場合は
     確認が求められ、サイトがメンテナンス中に、影響を受けるファイルが移動されます。
   - ライブラリをスキャンします。スキャンは、プロバイダーのメタデータを待たずに
     ローカルの作品を検出します。
   - アップグレードで以前のカスタムワークフローが引き継がれた場合は、それらを確認します。
     Kikoto は、プリセットと完全に一致するものを無効なトリガーに変換できます。一致しない
     定義はエクスポートできます。新規インストールや、カスタムワークフローのないアップグレード
     では、この手順はスキップされます。
   - 任意で、バックグラウンドで実行されるメタデータ同期を開始します。
   - 起動時およびフォルダーの変更時にスキャンを実行するかどうかを決めます。新規インストールでは
     どちらもオフで、後からワークフローでオンにできます。

**後で** を選ぶと、次回の訪問までセットアップが閉じます。以前のリリースからアップグレード
したインスタンスは、標準のレイアウトとスキャンのトリガーを維持しますが、ストレージプールへ
移行するかどうかを選ぶために、このセットアップが表示されます。プールへの移行では、残りの
セットアップ手順の前に新たなローカルスキャンが実行されます。移行中、管理者には進行状況が
表示され、他のユーザーにはメンテナンスの通知が表示されます。移行に失敗した場合は、
ディスクを確認してから再試行できます。

### ストレージプール

各ディスクまたはクラウドドライブを、データディレクトリの個別のフォルダーとしてマウントします。
例:

```yaml
volumes:
  - ./config:/config
  - ./cache:/cache
  - ./data:/data
  - /mnt/disk1:/data/disk1
  - /mnt/cloud:/data/cloud
```

Kikoto は、選択した各フォルダーに `.kikoto-pool` マーカーを書き込みます。ディスクが
マウントされていないとき、そのフォルダーは空でマーカーもないため、プールはオフラインとして
表示され、スキャンは作品を見つからないものとして報告せずに、そのまま変更しません。
取得（Fetch）は、ファイルを受け取るプール内でステージングと公開を行うため、各公開は 1 つの
ディスク上での名前変更になります。取得する前に、設定 -> ライブラリで Fetch プールを選択して
ください。それまでは、取得時に設定すべき内容が案内されます。

## ビルドを検証する

以下のコマンドはソースチェックアウトを検証するものです。リポジトリ全体の一貫したチェックには、
対応する [Makefile](../../../Makefile) のターゲットを使用することをお勧めします。

バックエンド（ソースチェックアウトのみ）:

```sh
cd backend
go test ./...
```

フロントエンド（ソースチェックアウトのみ）:

```sh
cd frontend
npm ci --strict-allow-scripts
npm run build
```
