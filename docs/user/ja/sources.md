# ソース
[English](../en/sources.md) · [简体中文](../zh-Hans/sources.md) · [繁體中文](../zh-Hant/sources.md) · [日本語](../ja/sources.md) · [한국어](../ko/sources.md)

ソースは、ファイルの出どころを表します。

## ソースの種類

- ローカルフォルダーソース。
- Kikoeru 互換のリモートソース。
- 移行済みの既存レコード専用の、従来の Number178 互換リモートソース。

## 現在の動作

- ローカルスキャンは、設定されたデータルート配下の、対応する作品コードのフォルダーを検出します。
- リモートソースのタブでは、すべての結果を取り込むことなく、設定済みのソースを閲覧できます。
- 作品詳細は、バックエンドの集約された利用可能状態の確認を使用します。
- リモート同期は、メタデータとソースのファイルツリーを統合データベースに取り込みます。
- リモートキャッシュは、選択したリモートファイルをキャッシュルート配下に実体化します。
- リモート取得（Fetch）は、選択したリモートファイルをローカルのデータツリーに昇格させます。
  既定のレイアウトは `/data/<source_code>/<code_prefix>_<code_group>/<work_code>` です。
  従来の `<source_name>` テンプレートトークンは、安定したソースコードの別名として引き続き
  受け付けられます。
- ソースごとに分離された保存テンプレートを使用する互換ソースは、マシン用のマーカーと
  多言語の `README.md` で、その Fetch ルートを占有します。Fetch が公開を直接登録するため、
  そのファイルの変更でローカルフォルダーのウォッチャーが作動することはありません。
  既に存在していて空ではなく、一致するマーカーのないルートは、ブロックする Fetch のレビュー
  競合として表示され、自動的に採用されることはありません。
- 古い Kikoto のバージョンで作成されたマーカーのないルートは、同じ元ソースに対する有効な
  `managed_fetch` のフォルダーの場所、または、成功した計画が同じソースと対象ルートを記録している
  成功した `remote_work_fetch` の実行から認識できます。Kikoto は、証明された作品サブツリーには
  立ち入らずに、それらの正確な履歴上の対象とその祖先に対してルート全体を検証します。
  ルート直下の通常の `README.md` は許可されますが、説明のつかないエントリ、リンク、
  リパースポイント、および対象が存在しない古いレコードがあると、ルートはブロックするレビューの
  ままになります。認識は読み取り専用で、次の Fetch でマーカーが書き込まれ、多言語の README は
  まだ存在しない場合にのみ追加されます。
- キャッシュとローカルの削除は、統合された作品ではなく具体的なファイルの場所を対象とします。
  混在した選択は、1 つの復旧可能なワークフローとして送信され、ローカルの削除では作品の進捗と
  聴取マークが保持されます。
- リモートソースの一覧と詳細ページは、ソース単位のビューのままにする必要があります。
  統合されたローカルの作品詳細モデルを置き換えるものではありません。
- 互換性のあるリモートの作品レスポンスは、ソースの現在の `price` を対応付けます。この値は
  価格履歴としては保存されず、正規の通常価格としても扱われません。
- デモモードは、リモートサーバーに接続することはありません。唯一のリモートソースである
  Remote Kikoeru は、許可されたローカルの作品からランダムに選んだものを元にプロセス内で
  シミュレートされ、ライブラリではその上にその旨の通知が表示されます。
- `kikoeru_compatible_number178` は、移行されたソース用にアダプターを保持していますが、
  新しいソースと構成シードの入力では拒否されます。過去の `kikoeru_compilable_number178` という
  綴りは自動的に移行されます。

## 利用可能状態の確認

起動時とソース変更時の一括確認では、まず関連するソースの正常性を検証します。このプローブは
`/api/health` を優先し、ヘルスエンドポイントを公開していない互換ソースには、1 件の一覧リクエストに
フォールバックします。

管理者は、設定 -> ライブラリから `POST /api/file-sources/{id}/health-check` を使って、同じ
制限付きプローブを手動で実行できます。レスポンスは、設定されている上流のアドレスや生の上流
エラーを返すことなく、正常性、確認時刻、所要時間を報告します。

ソースに到達できない場合、Kikoto はそのバッチではそのソースを利用不可としてマークし、作品ごとの
確認をスキップします。候補となるすべての作品を見つからないものとしてマークすることはありません。

## ダウンロードのペース配分

リモートのダウンロードは、設定された遅延を待機し、一時的なエラーはバックオフを付けて再試行します。
設定 -> キャッシュと取得では、ファイルごとのメディアのダウンロードサイズ上限も設定できます。
既定は 100 GB で、指定できる範囲は 1〜2048 GB です。この上限は、ソースがレスポンスサイズを
宣言していない場合でも、Fetch と再生キャッシュの実体化に適用されます。リモートと DLsite の
カバー画像には、別の固定の 20 MiB の上限が使用されます。DLsite のメタデータ同期も、プロバイダーの
商品とカバー画像のリクエストに対して、設定されたベース遅延とバックオフを使用します。

ソースがレート制限または一時的な利用不可のレスポンスを返した場合、Kikoto はそのソースが求める
時間だけ、そのソースへのリクエストを一時停止しますが、設定 -> キャッシュと取得の **最大待機時間**
を超えることはありません。そのソース向けのキューにあるジョブは、再試行回数を消費することなく
一時停止が終わるのを待ち、他のソースのジョブは継続されます。

Fetch の計画には、すでに完全に保存されているメタデータと、キャッシュされたソースの利用可能状態が
使われます。要求されたコードに DLsite のスナップショットや版の関係がない場合、準備段階で、
レビューを組み立てる前に、限定的な対象ファミリーの同期が実行されます。キューに入った Fetch は、
同じツリーをすぐに再度要求するのではなく、送信時に受け入れたリモートツリーを再利用します。
ローカルへの登録が成功した後、その Fetch で昇格したキャッシュオブジェクトは削除され、
選択されなかったキャッシュオブジェクトは引き続き利用できます。
